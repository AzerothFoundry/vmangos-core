# 可编辑决策框架：第一阶段

## 当前交付边界

本模块提供可编译、可测试的决策基础，供后续 PVE 职业循环、场景和 Boss 策略迁移。现有 PVP 引擎与 PVE 行为仍保留；**本轮没有把全部行为迁移到新框架，也不提供新的全职业／全 Boss 策略**。

原生接入只支持默认关闭的 shadow：收集观察、加载规则、排序并做只读原生施法预检查，绝不执行新动作。遭遇协调器目前由纯值类型 API 和离线测试驱动，尚未接入实际 Boss AI。没有生产部署或重启，不改客户端或数据库结构。

## 数据流与模块

```text
原生观察适配器 → Observation（值类型、场景／对象版本）
                         ↓
遭遇 Session → 注入共享阶段、职责与 epoch
                         ↓
JSON Policy → 命名谓词／组合条件 → Rank／Trace
                         ↓
Intent（owner、目标GUID、优先级、资源、有效期）
                         ↓
原生 Check → Arbiter → 原生执行器提交／拒绝 → 有界事件
```

| 文件 | 契约 |
| --- | --- |
| `BotDecision.h/.cpp` | Observation、Scope、能力目录、Intent、资源仲裁、执行器和有界事件 |
| `BotDecisionPolicy.h/.cpp` | 类型化字段、命名谓词、JSON 解析、规则排序、解释及只读版本发布 |
| `BotEncounter.h/.cpp` | 共享遭遇状态、职责分配、生命周期、阶段和策略固定 |
| `PveDecisionRuntime.h/.cpp` | PartyBot 的可选 shadow 观察与原生预检查 |
| `tools/ai/policy_tool.cpp` | 无网络、无执行能力的配置校验和离线决策工具 |

值类型决策与遭遇接口没有 Player／Unit 指针；原生适配入口本身接收 PartyBotAI 引用。规则引擎与遭遇模块可脱离游戏数据测试；原生适配器仍只能在原 AI 的安全更新上下文读取对象。不要将适配器直接放入外部推理线程。

## 编辑、检查与试算

需要 C++14 编译器；只使用仓库已有 nlohmann/json，无 Python 运行时或数据库依赖。可从任意工作目录调用构建脚本，示例中的相对配置路径则以仓库根为基准。

```sh
sh tools/ai/build-policy-tool.sh /tmp/azeroth-policy-tool
/tmp/azeroth-policy-tool catalog
/tmp/azeroth-policy-tool validate config/pve-decision.example.json config/pve-encounter.example.json

# 示例默认关闭。只给离线副本启用规则，不修改游戏配置。
jq '.enabled = true' config/pve-decision.example.json > /tmp/pve-policy-enabled.json
/tmp/azeroth-policy-tool evaluate /tmp/pve-policy-enabled.json config/pve-observation.example.json
```

`catalog` 显示注册字段和三个示例能力。字段已注册不等于所有生产者都能提供；原生 producer 支持的子集见下文。`evaluate` 输出候选和逐规则原因，不连接服务器、不触发动作。`unknown_observation` 表示缺数据，不能解释为技能一定不该释放。当前解释为规则级原因，还不提供逐叶表达式执行树或完整战斗回放。

编辑器可使用 [`policy.schema.json`](policy.schema.json) 校验结构和自动提示。C++ 解析器仍是最终裁判：它另外检查重复键、字段类型、能力目录、引用循环及展开预算。不要把 `$schema` 加进策略实例，当前运行时拒绝未知根字段。

## 条件与“优势／劣势”

不要先规定一个代表战局的万能分数。框架区分事实、组合判断与行动规则：

- 事实来自适配器：血量、蓝量、距离、控制、已学技能、技能冷却／GCD 就绪集合。
- `predicates` 将事实组合成可复用判断，例如资源充足、某个控制技能可用、允许输出的阶段；名称不会自动产生新的感知能力。
- `when_expr` 支持 `all`、`any`、`not`、`ref` 任意受预算约束的嵌套。规则还支持原有 `when` 全满足、`any` 至少满足一个，以及条件性 `adjust` 分数。
- 数值、布尔、文本和 ID 集合均有明确类型。缺失为 Unknown；取反仍是 Unknown，不能通过“没有观察到”推导“确认不存在”。已知空集合 `[]` 与字段缺失不同。

例如资源充足且逃生技能已就绪，可以参与进攻倾向判断；缺少敌方关键 CD 观察时，该条件不能装作已知。当前原生 shadow **不提供敌方 CD 推断**，也未提供所有自身技能的剩余毫秒数。`self.ready_spells` 只是自身技能原生 CD/GCD 的已知状态，不能单独代表法术最终可施放。

多条件可通过命名谓词、额外优先级和场景条件表达；确实无法覆盖时，先补数据生产与语义，再决定是否引入更复杂决策器。当前没有模型、强化学习或在线自学习。

## 场景与职责覆盖

规则可通过注册字段 `scene.kind`、`self.class`、`self.role`、`target.entry`、`encounter.id`、`encounter.phase` 和 `assignment.role` 组合职业、野外、普通副本、团本及阶段特例。

这版使用条件与优先级表达覆盖，没有隐式“Boss 文件一定盖过职业规则”的魔法顺序。命中规则按最终分数降序，同分按规则 ID 排序；建议不同 owner 表明来源，例如 rotation／encounter／emergency。协调器分配的职责槽位名注入 `assignment.role`，与原生数值职责 `self.role` 是两种不同信息。

策略 JSON 只能引用 C++ 能力目录中的能力名和允许的目标。法术 ID、资源掩码和动作实现由受信任程序注册，配置不能授予 GM、SQL、绕过 CD/GCD、任意脚本或直接坐标传送能力。能力注册目录目前是可扩展的数据结构，不是可从 JSON 加载任意插件的执行系统。

第一阶段示例能力仅为破甲、寒冰箭和自疗的首级技能，用于验证契约；它们不做自动最高等级解析，不构成成熟循环。Move／Interact／Wait 已有类型契约，但当前原生适配没有这些执行能力，也没有开放真实 Cast 执行。

## 版本与热更新

- `Store::Stage` 完整校验后生成 pending，不改 active；失败保留之前有效的 active 和 pending。
- `PublishAtBoundary` 是调用者明确确认安全边界后发布。`ReloadNow(text, true)` 是一体化显式发布；两个分步调用若有多个写者，调用者须串行协调。
- 发布产生单调 generation，读者持有不可变快照；旧读者不会看到半份新配置。
- 遭遇 Session 深复制规则与阶段定义，直到结束／失败再开始新尝试才换版本；每个成员读取同一 Session 的 Policy。
- 原生 shadow 全局至多每秒读一次固定配置路径，每角色至多每秒采样；坏文件保留 last good。角色战斗期间固定自己的规则版本，脱战后采用新版本。此处仅为 shadow 安全边界，不等于全团原生遭遇热更已接入。

部署者应先写临时文件，再在同文件系统原子替换配置。读到非法／截断配置会保留旧版本；但如果非原子写入中间内容本身合法，程序无法判断它是否为作者最终意图。

## 遭遇与团队共享状态

Key 使用地图、副本实例、团队 ID、遭遇 ID 和 attempt 隔离。Session 是调用方拥有的单写者对象；authority 表达由谁驱动协调，不是网络认证令牌。当前没有全局 Session 注册表、任意 Boss 识别或原生团长迁移适配。

生命周期为 Preparing → Combat → Recovering／Completed／Failed；恢复到准备会重置初始阶段和计时。阶段转换每个有效观察最多一次，可设置最短停留时间，缺字段不触发。首次版本只提供阶段 `all` 条件；通用规则的嵌套谓词不代表阶段条件也已支持相同完整语法。

职责配置按槽位顺序保留合法存活成员，再确定性地补空位；显式报告缺额，同一成员不占多个槽位。它不是最优匹配求解器：通用槽位可能抢走专用槽位候选，配置应把受约束槽位优先列出。新增人员不会无故重新洗牌已分配成员。

阶段、生命周期或实际分工变化递增 epoch。`Annotate` 在范围校验后为每个成员注入共享阶段、本人职责和 epoch；`Rank` 把遭遇 ID／attempt／epoch 绑定进 Intent。执行前再次核对，防止阶段切换或灭团重开后仍执行旧策略。

## 仲裁与执行安全

Intent 绑定角色生命周期、场景、组、目标 GUID、策略版本和有效期。校验拒绝旧场景、未来观察、过期、目标变化或旧遭遇 epoch。它没有证明观察之后的所有数值仍然不变；实际执行器必须重新检查有关事实。

资源包括移动、施法、交互。多资源先全部检查再占用，避免部分抢占；相同优先级不抢别人，不可抢占动作需要显式结束。相同 owner/rule 换动作也不能偷偷绕过原有资源保护。

**租约不等于已经取消原生动作。** `Dispatch` 将被替换动作显式传给 Executor；真实执行器必须保证重新校验、取消／替换与提交新动作的契约。失败表示没有提交副作用，包括不能先取消旧动作再报告失败；不能满足就应拒绝。本轮仅实现拒绝执行的 shadow 适配器，假执行器测试不代表原生动作抢占已经验收。

事件有固定容量和字符串上限，记录观察／策略／遭遇身份、owner、规则、阶段和原因。缓冲由调用方 drain；没有后台持久化 JSONL writer、完整回放、奖励或训练数据流水线。没有把记录每个事件视为可无限扩展的零成本功能。

## 原生 shadow 使用范围

配置示例（服务端需包含本分支代码）：

```ini
PveDecision.Shadow = 0
PveDecision.PolicyFile = ""
```

显式打开 shadow 并给策略文件路径后，必须在策略 JSON 中启用规则才有候选。服务器配置热重载沿用原有机制；JSON 内容则由 shadow 自己检查。这里只提供技术入口，没有在 GM／网页添加编辑面板。

可观测字段：自己职业／职责／等级／血蓝／存活／战斗／移动／施法／控制、当前地图类型、原生 CD/GCD 就绪集合，以及当前合法、同图、可见且 LOS 内的 NPC 目标 ID、血量和距离。不会为了本框架主动开怪、扫描全部附近敌人或读取敌方隐藏 CD。首级技能若已被更高等级替代，预检查可能明确拒绝 `not_known_by_actor`。

原生角色仍按旧 AI 行为行动；shadow 不发技能、移动、交互或账号数据库操作。关闭时不会读策略文件或采样目标。开启后热载仍在更新线程同步做有大小限制的文件读取，未完成规模性能测试，不能据此承诺数千 Bot 的开销。

## 验证与后续迁移

```sh
python3 tests/run_decision_foundation.py
```

该脚本在临时目录编译 C++14 真模块并测试：场景／目标／有效期与资源仲裁、失败回退和 shadow；规则解析、三值逻辑、命名引用、预算、热发布与并发快照；遭遇隔离、固定版本、稳定补位、阶段切换和旧 epoch；离线工具的真实示例及错误输入。

建议后续顺序：先让一个职业的基础 PVE 循环经真实执行器和逐角色开关接入；再接一处原生遭遇的共享 Session；之后增加治疗／坦克与复杂 Boss、统一 PVP 适配。每一步先 shadow 对照，再用专用测试角色验证失败、抢占和恢复，最后才扩大上线。全职业迁移和完整 Boss 策略不在此次完成声明中。
